# note素材ログ運用仕様(41_notelog_spec.md)

> 目的: 開発過程の「やったこと・詰まったこと・解決法」を作業のたびに記録し、
> あとから note 記事の題材として取り出せる資産にする。
> **記録はすべて Claude Code が作業のついでに行う。ケンの追加作業はゼロが原則。**

---

## §1. 仕組みの全体像

```
作業(Claude Code) ──毎タスク完了時──▶ docs/NOTELOG.md に追記(§3テンプレ)
                                          │
フェーズ完了 or 月1回 ──指示1行──▶ ★2以上を抽出して記事骨子を自動生成
                                          │
[👤ケン] 骨子を読んで書きたいものを選ぶ ──▶ note記事化
```

- ログは**リポジトリごと**に `docs/NOTELOG.md`(モノレポは1冊に集約、アプリ名列で区別)
- Claude.ai 側でやった作業(戦略立案・設計議論)は、セッション末にケンが「今日の分をNOTELOG形式でまとめて」と頼めばチャット側で生成できる → コピーして NOTELOG.md に貼る

## §2. Claude Code への組み込み(CLAUDE.md に以下を追記)

各リポジトリの `CLAUDE.md` に次のブロックを**そのまま追加**する。これで毎セッション自動で効く:

```
## NOTELOGルール(必須)
タスク完了ごとに docs/NOTELOG.md へ1エントリ追記(docs/41_notelog_spec.md §3形式)。
- 詰まり・エラー・想定外が発生したら、解決した時点で必ず記録(エラーメッセージは原文1行引用)
- 順調だったタスクも「やったこと」1行は残す
- 記録は事実のみ・各項目1行・テンプレ厳守。感想や冗長な経緯は書かない
- スクリーンショットを撮ると記事映えする瞬間(初回描画成功・ビフォーアフター等)には 📷 を付ける
```

## §3. エントリテンプレ(厳守・1エントリ最大7行)

```
### 2026-06-15 | railmap | N02前処理パイプライン
- やったこと: シェープファイル→GeoJSON変換と路線ID付与を実装
- 詰まり: geopandasのto_crsで距離が異常値(総延長80万km)
- 原因→解決: 投影前に度単位のままlength計算していた→EPSG:6933投影後に計算で解決
- 記事ネタ度: ★★★ / タグ: #GIS #geopandas #ハマりどころ 📷
```

### 各項目のルール
| 項目 | ルール |
|---|---|
| 見出し | 日付 \| アプリ名 \| タスク名(SPEC の§番号があれば併記) |
| やったこと | 必須。1行 |
| 詰まり | なければ「なし」と書き、原因→解決の行は省略 |
| 原因→解決 | 「◯◯が原因→◯◯で解決」の1行型。試行錯誤した場合は試した回数だけ書く(例: 3案目で解決) |
| 記事ネタ度 | ★1: 自分用メモ / ★2: 記事の一段落になる / ★3: **他の人も必ず踏む罠・記事1本の主役級** |
| タグ | 技術タグ2〜3個。後の検索・記事グルーピング用 |

### ★3の判定基準(Claude Codeが迷ったら)
「公式ドキュメントに書いていない/エラーメッセージから原因が想像できない/解決に30分以上かかった」のいずれかに該当すれば★3。

## §4. 記事骨子の自動生成(取り出しフェーズ)

フェーズ完了時または月1回、Claude Code に次の1行を指示する:

```
NOTELOG.mdの未処理分から記事骨子を生成。41_notelog_spec.md §4の形式で notes/draft-YYYYMM.md へ
```

### 骨子の出力形式(notes/draft-YYYYMM.md)
1. **候補記事リスト**: ★3エントリを核に、タグが近い★2を束ねて記事案を3〜5本提案(仮タイトル+想定読者+使用エントリ一覧)
2. **各記事案の骨子**: 導入(何を作ったか)→ ハマった点(エントリ原文引用)→ 解決(コード断片の挿入位置を指定)→ 学び
3. 処理済みエントリには NOTELOG.md 側に `[draft済]` を付記(二重使用防止)
- **本文は書かない。骨子まで**(文体・体験談はケンの声で書くのが note の価値。AIは構成係に徹する)

## §5. 運用上の注意

- NOTELOG.md は git 管理に含める(リポジトリが消えない限り素材は消えない)が、**公開リポジトリの場合に書いてはいけないもの**: トークン・秘密情報・収益の生数字・個人を特定する内容。該当はプライベートメモへ
- エントリが200件を超えたら年別ファイルに分割(`NOTELOG-2026.md`)
- 記事化したらエントリに `[公開済: 記事URL]` を付記 → どの知見が反応を得たかが分かり、次に書くべき記事の判断材料になる(=このログ自体も計測対象)

## §6. 初期セットアップ指示例(リポジトリごとに1回)

```
docs/41_notelog_spec.mdを読み、CLAUDE.mdに§2ブロックを追記、docs/NOTELOG.mdを見出しのみで作成。以後全タスクでNOTELOGルール適用
```
